1. Introducción

Los servicios web y las Interfaces de Programación de Aplicaciones (API) de arquitectura REST representan la columna vertebral de la integración de sistemas modernos. Permiten la comunicación agnóstica entre plataformas heterogéneas (clientes móviles, aplicaciones web SPA y bases de datos transaccionales), empleando el protocolo HTTP como estándar de transporte y esquemas JSON para el intercambio ligero de datos.

En estricto cumplimiento con la evidencia GA7-220501096-AA5-EV01: Diseño y desarrollo de servicios web - caso, este documento presenta el diseño arquitectónico, la implementación del código fuente y las pruebas de validación de un servicio web RESTful especializado en Registro e Inicio de Sesión de Usuarios. Siguiendo las directrices de la Guía 7, el servicio recibe usuario y contraseña, emitiendo mensajes explícitos de "Autenticación satisfactoria" o "Error en la autenticación", garantizando la encriptación de claves mediante algoritmos criptográficos con sal (Salt + Scrypt/BCrypt) y emitiendo tokens JWT para sesiones sin estado.

3. Diseño Arquitectónico del Servicio Web

3.1 Flujo Operativo del Caso: Registro e Inicio de Sesión

[Cliente Web / Móvil / Postman] │ │ 1. POST /api/auth/register { usuario, password, email } ▼ [Controlador Auth: Valida campos y verifica duplicados] │ │ 2. Genera Salt aleatorio y aplica Scrypt/BCrypt Hash ▼ [Almacenamiento: Guarda { id, usuario, email, salt, hash }] │ │ 3. Respuesta HTTP 201 Created ("Usuario registrado satisfactoriamente") ▼ [Cliente Web / Postman] │ │ 4. POST /api/auth/login { usuario, password } ▼ [Controlador Auth: Recupera Salt y compara Hash] │ ┌─────┴────────────────────────────────┐ ▼ ¿Credenciales Válidas? ▼ [ SÍ - Coincide ] [ NO - No coincide ] │ │ 5. Genera Token JWT (24h) 5. Retorna HTTP 401 Unauthorized 6. Retorna HTTP 200 OK "Error en la autenticación" "Autenticación satisfactoria"

3.2 Especificación de Códigos de Estado HTTP

Código HTTP Nombre Semántico Escenario de Uso en el Servicio
200 OK Éxito Autenticación satisfactoria (Login) y consulta de perfil protegido.
201 Created Creado Registro exitoso del nuevo usuario en el sistema.
400 Bad Request Petición Inválida Faltan campos obligatorios o no cumplen longitud mínima.
401 Unauthorized No Autorizado Error en la autenticación (usuario o contraseña incorrectos) o token ausente.
409 Conflict Conflicto El nombre de usuario o correo electrónico ya existe.

4.1 Endpoint de Registro: POST /api/auth/register

Cuerpo de la Petición (JSON):

Respuesta Exitosa (HTTP 201 Created):

{ "success": true, "mensaje": "Usuario registrado satisfactoriamente", "user": { "id": 1, "usuario": "karencampo", "email": "karen.campo@sena.edu.co", "nombre": "Karen Yuliana Campo", "rol": "ADMINISTRADOR", "fechaRegistro": "2026-11-08T22:45:00.000Z" } }

4.2 Endpoint de Login: POST /api/auth/login

Cuerpo de la Petición (JSON):

Respuesta Exitosa (HTTP 200 OK):

{ "success": true, "mensaje": "Autenticación satisfactoria", "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOjEsInVzdWFyaW8iOiJrYXJlbmNhbXBvIn0...", "tokenType": "Bearer", "expiresIn": "24h", "user": { "id": 1, "usuario": "karencampo", "nombre": "Karen Yuliana Campo", "email": "karen.campo@sena.edu.co", "rol": "ADMINISTRADOR" } }

Respuesta Fallida (HTTP 401 Unauthorized):

{ "success": false, "error": "UNAUTHORIZED", "mensaje": "Error en la autenticación: Credenciales inválidas. Contraseña incorrecta." }

5. Implementación de Seguridad Criptográfica

5.1 Hashing de Contraseñas con Sal Aleatoria

En concordancia con los estándares de ciberseguridad OWASP, el servicio jamás almacena contraseñas en texto plano. Cada contraseña se procesa mediante una sal criptográfica generada de forma aleatoria (crypto.randomBytes(16)) y una función de derivación de claves Scrypt/PBKDF2 de alta resistencia:

// Fragmento de server.js: Hashing criptográfico con sal function hashPassword(password, salt) { return crypto.scryptSync(password, salt, 64).toString('hex'); }

5.2 JSON Web Tokens (JWT) para Autenticación Stateless

Una vez validada la autenticación, el servidor genera un token JWT compuesto por tres segmentos codificados en Base64Url y firmados con HMAC-SHA256:

  • Header: Define el algoritmo de firma (HS256) y el tipo de token (JWT).
  • Payload: Transporta los reclamos del usuario (identificador, nombre de usuario, rol y vigencia de 24 horas).
  • Signature: Garantiza que el contenido del token no pueda ser adulterado por terceros.
